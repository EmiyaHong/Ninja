# Ninja · 面试 Demo 进度清单

更新：2026-10-23（Asia/Taipei）  
目标岗位：游戏策划 / 战斗策划。用户还希望未来可能将其发展为完整游戏。  
本文件是推进建议与验收清单，不代表下列全部功能已经获准开工或参数已经确认。每次先完成一段可玩增量，讨论反馈后再安排 Sol 实现下一段。

## 首个交付目标

建议范围：一个玩家、一只几何熊 Boss、一个统一风格的竞技场，包含简短教学、完整战斗、胜负和重试。新玩家用约 3–5 分钟体验核心特点；教学先以约 30–60 秒为调节目标，实际以试玩为准。

展示重点：连续手势控刀如何产生可理解的攻防选择；如何解决回程成本；敌人如何用方向、节奏和收招创造机会；玩家如何把接招成功转化为进攻收益。精致度落实在跟手、可读、反馈一致、画面统一和流程完整上。

暂缓：第二只 Boss、多关卡、装备养成、复杂技能树、剧情演出、多人和多平台。不是取消完整游戏愿景，而是先用一个完成度较高的战斗片段验证方向。

## 阶段 0 · 留住可恢复的起点

- [x] 建立本地 Git 仓库和第一份可运行基线，核对忽略缓存、临时文件及敏感配置；单独保留必要美术源文件。（2026-10-23，`49f627e`）
- [ ] 建立开发调试和正式试玩两套参数，避免玩家生命 10000、宽容窗口等调试设置进入成品。
- [ ] 每个阶段交付标记版本、操作说明、已知问题和证据位置。

**验收**：可以恢复到本轮原型；开发调参与试玩调参不会互相覆盖。此阶段不擅自发布远程仓库。

## 阶段 1 · 定下舒服的手势规则（当前优先）

- [x] 收到PC初步试玩反馈：用户认为“交替和同向操作还算挺舒服”（2026-10-23）；未报告具体组数或最终A/B偏好。
- [ ] 必要时补充 A 同向、B 同向、B 交替的可比较记录；原建议每种3组仅为试验安排，不视为已完成。
- [x] Sol已新增按5进入的方向手势对熊战斗，按1恢复自由控刀，镜头/站位不变（2026-10-23，`2bef91d`）；见 [试玩说明](方向手势实验试玩说明.md)。
- [ ] 用户比较方向手势与自由控刀的跟手性和攻防衔接；两模式默认参数不同，比较难度前需统一参数。
- [ ] 记录回位空间、手腕负担、方向理解、判定失误和能否通过乱摇接招；区分操作失败与识别失败。
- [ ] 仅针对反馈调整距离、速度、转向资格与窗口，一轮尽量只改一类变量。
- [ ] 确定正式规则；若水平实验无法覆盖判断，再补竖直/斜向小样后决定，不提前批量做招式。
- [ ] 在正式战斗中验证选定规则，解决普通攻击冷却与防守衔接问题；是否改动共享冷却根据实际反馈决定。

**验收**：用户能说明为什么一次成功、一次失败；短幅自然运动足以操作，连续交锋没有必须大幅搬动鼠标的明显负担。保留落选模式作实验记录，不必同时作为正式玩法。

**输出**：一页正式输入规则 + A/B 取舍记录 + 可玩的基础版本。

## 阶段 2 · 做出一场有起伏的 Boss 战

- [ ] 为几何熊写招式表：前摇信号、方向、命中时刻、连段衔接、可反击窗口、风险与奖励。
- [ ] 用现有三种基础动作组合约 3–4 套招式：单发、交替连段、延迟终结等；以阶段 1 的自然手势为约束。
- [ ] 明确读招 → 接招 → 反攻 → 破防爆发的转换，普通命中、弹反和易伤各自有清楚价值。
- [ ] 根据试玩决定是否需要脱压架势恢复、低血恢复变慢、施压反击；这些是候选机制，不默认全部加入。
- [ ] 建立正式试玩伤害和容错，让贪刀有代价、失败能理解；检查某次受伤后是否会无解地连吃下一击。
- [ ] 后半程如需变化，优先重组已学会的招式/节奏，再考虑新机制，避免突然增加未教过的操作。

**验收**：用户能完整打赢或失败；主动进攻和接招都有理由；全程乱划或只等机会不会明显优于理解规则后的操作。目标战斗时长由实际试玩调整，不仅靠增加血量延长。

**输出**：一场可从开战到结算的 Boss 战 + 招式表/数值表。

## 阶段 3 · 把每次命中和接招做清楚

- [ ] 普通命中、弹反、受伤、破防、胜利有可区分的声音及视觉反馈；先覆盖关键事件，再加环境音乐。
- [ ] 配好蓄力、挥击、接触、回震和收招，视觉落点与判定时刻一致。
- [ ] 小幅打击停顿/震动作为可选反馈；同步暂停输入时间与招式时间，不使停顿造成误判；提供减弱震动的设置。
- [ ] 控制火花、刀迹、闪白和提示的遮挡，任何时候都能读出下一招。
- [ ] 校准“爪与玩家在画面上有距离”的表现：用清楚的挥击轨迹/攻击提示解释威胁，必要时调整构图或动作，避免凭空扣血。

**验收**：不用盯数值日志也能分辨五类结果；关闭音频仍能读招，开启音频能进一步理解节奏。更华丽的效果没有降低可读性。

## 阶段 4 · 统一画面与界面

- [x] 绘制构图和光影目标图，参考现有geocat、geobear和UI Kit；见 [v02设计规范](视觉目标与美术规范.md)（2026-10-23）。
- [ ] 用户确认目标图的场景、冷暖光、构图、UI和字体方向；玩家仍为占位背影。
- [ ] 将占位玩家与武器升级为匹配几何熊的简洁造型，保留意念控刀特色。
- [ ] 完成一个有地面、阴影、前后层次的竞技场；视觉焦点留给敌人动作和玩家刀尖。
- [ ] 收敛 HUD 为生命、架势、必要状态；把大量训练参数和快捷测试入口移入开发/训练界面。
- [ ] 完善开战、受击、破防、死亡/胜利的动作衔接；修复关节拼接、脚底漂移和遮挡问题。
- [ ] 检查常见窗口尺寸下文字、血条和操作区域，确保信息不挤压/裁切。

**验收**：随机截取待机、交锋、破防三张图，均有统一的视觉风格和清楚层次；没有明显占位元素、调试文本或特效遮住关键动作。沿用已有可用素材，不因统一风格无理由重做全部资产。

## 阶段 5 · 让陌生人独立玩完

- [ ] 简洁标题页：开始、训练、设置、退出；明确游戏名称和鼠标操作。
- [ ] 以操作教学串联“挥刀命中 → 接一刀 → 接一组 → 破防输出”，每次只教当前需要的一件事。
- [ ] 正式战斗逐渐减少箭头/文字依赖；是否保留辅助提示由可读性试玩决定。
- [ ] 完成入场、战斗、胜负、重试与返回；失败后少量操作即可重来。
- [ ] 补齐音量、窗口/全屏、暂停/失焦、恢复输入及退出行为。

**验收**：邀请至少一位未参与开发的人，在不口头指导的情况下进入战斗、理解基本操作、失败后自行重试。记录真实卡点后调整教学；若暂时没有测试者，明确标记未验收。

## 阶段 6 · 打包、稳定性与面试材料

- [ ] 导出 Windows 试玩包，验证不依赖 Godot 编辑器；发布配置不带开发用 MCP 服务或测试入口。
- [ ] 完整走完首次启动、教学、胜负、重试、暂停、切窗和退出；持续试玩至少 10 局作为建议检查目标，真实记录结果。
- [ ] 在实际目标机器检查画面/输入流畅性，针对故障再扩展测试，不把脚本时间步测试写成真实帧率测试。
- [ ] 整理素材与音频来源、使用许可、署名，以及 AI/工具辅助范围。
- [ ] 录制约 60–90 秒实机展示：特色输入、读招接招、破防爆发、完整视觉；视频时长为建议。
- [ ] 准备策划说明：目标体验、循环图、招式设计、规则与数值关系、A/B 实验、反馈驱动修改、未解决问题。
- [ ] 用真实反馈填写对比表：规则理解、回位负担、主要失败原因、主观偏好；可记录首次学会/通关时间，但不编造样本或提升百分比。

**验收**：陌生电脑上可启动并完成体验；有可运行包、实机视频和简洁设计说明；能解释至少一次“为什么放弃某方案、依据是什么”。

## Demo 后再决定完整游戏方向

复用当前输入、战斗事件、可配置招式、训练入口和验证方法；当第二只敌人需要它时，再提炼真正重复的逻辑，不提前造庞大通用框架。

完成上述 Demo 并收到外部反馈后，再验证：不同敌人能否产生不同手势决策；连续多场是否疲劳；核心战斗能否支撑关卡节奏。通过这些验证后，才扩展第二敌人、小关卡、成长和叙事。

## 每轮推进方式

1. 本聊天确定一个具体目标和验收方式。
2. Sol 实现一个可试玩增量，并写清实际验证结果。
3. 用户试玩并描述“发生了什么、期望什么、哪里不舒服”。
4. 本聊天更新设计日志、本清单状态和下一步。
